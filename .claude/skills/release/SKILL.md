# 릴리스

사용자는 **시작만 한다.** 그 뒤로 묻지 않는다. 대신 되돌리기 어려운 자리마다
**독립된 에이전트에게 점검을 받고**, 통과 못 하면 **중단하고 보고한다** —
사용자에게 되묻지 않는다. 그게 승인 없는 파이프라인의 유일한 정직한 계약이다.

> **왜 안 묻나**: 물어보면 자동화가 아니다. **왜 그냥 진행하지 않나**: 이 배포는
> 유저의 **메일함 전체를 읽는 권한으로 도는 코드**를 내보낸다. 사람이 안 보면
> 다른 눈이 봐야 한다.

## 절대 어기지 않는 것

- **실패하면 멈춘다.** 우회하지 않고, 다시 시도하지 않고, 사용자에게 묻지 않는다
- **배포 번호를 추측하지 않는다.** API 응답으로 받은 정수만 쓴다
- **등급을 `scripts/impact.js` 의 하한보다 낮추지 않는다.** 올리는 건 자유다
- **`build/` 밖의 파일을 배포하지 않는다**

## 0. 준비 확인

```sh
git status --short          # 깨끗해야 한다. 아니면 중단
git branch --show-current   # main 이어야 한다
npm run check               # 전부 초록이어야 한다
```

하나라도 어긋나면 **여기서 멈추고** 무엇이 걸렸는지 보고한다.

`~/.config/k-money/deploy.json` 이 없으면 배포 단계에서 죽는다. 미리 확인한다.
처음이면 `node scripts/deploy.js --snapshot-manifest` 로 라이브러리 매니페스트를
저장소에 내려받아 커밋해 둔다.

## 1. 무엇이 바뀌었는지 **측정한다**

```sh
node scripts/impact.js --json
```

이게 등급의 **하한**을 준다. 감으로 매기지 않는다.

`docs/sample-latest.json` 은 진짜 파이프라인을 통과한 산출물이고 CI 가 최신임을
강제한다. 직전 태그의 것과 비교하면 "유저가 보는 숫자가 실제로 바뀌었는가" 가
측정된다.

### 측정이 못 보는 축 — 여기서만 등급을 올린다

`impact.js` 는 산출물의 차이만 본다. 아래는 **직접 diff 를 읽고 판단**한다.
하나라도 걸리면 🔴 이다.

- **권한** — `appsscript.json` 의 `oauthScopes` 가 늘었는가
- **프라이버시** — AI 나 드라이브로 나가는 항목이 늘었는가. 가게 이름·병원처럼
  **재식별이 되는 값**이 새로 포함되는가
- **유저 파일** — 지우거나 덮어쓰는 코드가 바뀌었는가 (`메모리/` 정리 로직)
- **잘못된 안내** — 이전 버전 문서가 이제 **사실이 아니게** 되었는가.
  0.4.2 가 🔴 였던 이유가 이것이다: SECURITY.md 의 문장이 거짓이 됐다

## 2. CHANGELOG 초안

`CHANGELOG.md` 맨 위(머리말 `---` 바로 아래)에 새 항목을 쓴다.

```
## X.Y.Z — YYYY-MM-DD · 라이브러리 버전 대기
```

**`대기` 로 쓴다.** 배포 뒤 `record-deploy.js` 가 채운다. 중간에 실패했을 때
틀린 번호가 박혀 있는 것보다 빈 자리가 보이는 게 낫다.

### 문체 — 기존 항목이 규칙이다

읽는 사람은 개발자가 아니라 **뱅샐 쓰는 사회 초년생**이다.

| | |
|---|---|
| 쓰는 것 | 존댓말. "당신이 뭘 해야 하나" |
| 안 쓰는 것 | 커밋 요약. "무엇을 고쳤나" |
| 구조 | 등급 한 줄 → 굵은 소제목(유저의 말로) → 서사 → 인용 블록 예시 → "다만 ~는 그대로예요" |
| 우리 실수 | **인정한다.** "0.4.1 이 문제를 오히려 키웠습니다" 가 이 저장소의 문체다 |
| 남는 제약 | 숨기지 않는다. 마지막에 관련 문서 링크 |

`0.4.1`·`0.4.2`·`0.4.3` 항목을 먼저 읽고 그 결에 맞춘다.

### 버전 크기

`patch` 가 기본이다. 공개 API(`library-api.gs`)의 함수 이름이나 인자가 바뀌면
`minor` 다 — 유저가 버전을 고정해 쓰므로 그 계약이 깨지는 건 다른 종류다.

## 🚦 점검 1 — 릴리스 계획

`Agent` 를 **일반 에이전트로 셋** 띄운다. 각각 다른 각도를 준다.
사용자에게 묻지 않는다. **셋 중 둘 이상이 FAIL 이면 중단한다.**

각 에이전트에게 주는 것: `impact.js --json` 출력, `git diff <직전태그>..HEAD`,
CHANGELOG 초안, 기존 CHANGELOG 항목 셋.

| 에이전트 | 물을 것 |
|---|---|
| **등급** | 이 등급이 **너무 낮지 않은가.** 측정이 못 본 축(권한·프라이버시·유저 파일·거짓이 된 문서)을 diff 에서 직접 찾아라. 하나라도 있으면 FAIL |
| **문체** | 유저가 이걸 읽고 **올릴지 말지 정할 수 있는가.** 커밋 요약처럼 읽히는 문장, 개발자만 아는 용어, 남는 제약을 숨긴 곳을 찾아라 |
| **사실** | 초안의 주장이 **diff 와 맞는가.** 안 한 걸 했다고 썼거나, 한 걸 빠뜨렸거나, 숫자가 틀린 곳을 찾아라 |

각 에이전트는 `PASS` 또는 `FAIL` 과 이유를 반환한다. FAIL 이면 그 이유를 반영해
초안을 고치고 **다시 셋을 띄운다.** 두 번째도 FAIL 이면 **중단하고 보고한다** —
같은 지적을 세 번 받으면 그건 초안 문제가 아니라 변경 자체의 문제다.

## 3. 버전 올리고 커밋

```sh
npm version patch --no-git-tag-version   # VERSION · README · container.gs · core.gs
npm run check                            # 버전이 세 곳에서 맞는지 본다
git add -A && git commit                 # 메시지는 "X.Y.Z — <무엇을 깨달았나>"
```

커밋 메시지는 저장소 결을 따른다 — `git log` 의 최근 것들을 보면 **무엇을
고쳤나가 아니라 무엇을 알게 됐나**를 적는다.

## 4. 빌드

```sh
node scripts/build-deploy.js
```

`build/library/` 와 `build/template/` 이 생긴다. 화이트리스트라 목록에 없는 건
안 나가고, 목록에 있는데 없으면 죽는다.

---

## 🚦 점검 2 — 나가기 직전

**여기부터 밖으로 나간다.** 에이전트 **하나**를 띄워 `build/` 를 검사시킨다.
FAIL 이면 중단한다.

주는 것: `build/` 전체 목록과 내용, `appsscript/appsscript.json`, `git status`.

물을 것:

- `build/library/` 에 정확히 `core.gs zipcrypto.gs app.gs library-api.gs` 넷뿐인가.
  `template.gs` 나 다른 게 섞이지 않았는가
- `build/template/` 에 `container.gs` 와 `appsscript.json` **둘 다** 있는가
- 매니페스트의 `oauthScopes` 가 `docs/install.md` 의 스코프 표와 **정확히 같은가**
- `developmentMode` 가 `false` 인가
- 어느 파일에도 **비밀번호·토큰·실데이터**가 없는가
- `core.gs` 가 지금 `core/` 에서 나온 것인가 (`npm run check` 가 보지만 한 번 더)

## 5. 라이브러리 배포

```sh
node scripts/deploy.js --library
```

이게 하는 일: 원격 매니페스트를 읽어 그대로 되쓰고 → 파일을 올리고 →
배포를 만들어 **번호를 응답으로 받고** → 그 버전을 되읽어 **바이트 대조**한다.
대조가 틀리면 스스로 죽는다.

마지막 줄의 `LIBRARY_VERSION=N` 에서 번호를 가져온다. **화면에서 읽지 않는다.**

## 6. 번호를 세 곳에 적는다

```sh
node scripts/record-deploy.js <N> --note "<한 줄 요약>"
```

CHANGELOG 의 `대기`, `docs/deploy.md` 이력표, `appsscript/appsscript.json` 의
라이브러리 참조를 한 번에 채운다. 하나라도 못 고치면 아무것도 안 고치고 죽는다.

## 7. 템플릿 배포

```sh
node scripts/build-deploy.js --lib-version <N>
node scripts/deploy.js --template
```

`container.gs` 와 `appsscript.json` 이 **한 번의 요청으로** 나간다. 갈릴 수 없다.

> 이걸 빠뜨리면 **새로 사본 뜨는 사람이 옛 라이브러리를 받는다.** 오류 없이,
> 조용히. 이 파이프라인에서 가장 조용한 실패라 자동화의 핵심 이유이기도 하다.

---

## 🚦 점검 3 — 공개 직전

에이전트 **하나**를 띄워 저장소 정합성을 검사시킨다. FAIL 이면 중단한다.

- CHANGELOG 최신 항목의 배포 번호가 실제 배포한 `N` 과 같은가
- `docs/deploy.md` 이력표 마지막 행이 `N` 인가
- `appsscript/appsscript.json` 의 라이브러리 참조가 `N` 인가
- `VERSION` · `package.json` · `container.gs` · `README` 의 버전이 다 같은가
- `npm run check` 가 초록인가
- **지난 CHANGELOG 항목에 `대기` 가 남아 있지 않은가**

## 8. 공개

```sh
git add -A && git commit -m "라이브러리 배포 번호는 <N>"
git tag -f vX.Y.Z && git push origin main && git push --force origin vX.Y.Z
gh release create vX.Y.Z --title "X.Y.Z — 라이브러리 버전 <N>" --notes-file <해당 절>
```

태그는 **번호가 채워진 최종 커밋**에 둔다. `대기` 가 박힌 상태로 릴리스가
나가면 그걸 읽는 유저가 드롭다운에서 무엇을 고를지 모른다.

## 9. 보고

사용자에게 한 번에 알린다: 버전 · 라이브러리 번호 · 등급과 그 근거 ·
점검 다섯 번의 결과 · 릴리스 URL · CI 상태.

중단했다면 **어디서 왜 멈췄는지**와 지금 저장소가 어떤 상태인지(커밋됐는지,
배포가 나갔는지) 분명히 적는다. 반쯤 나간 상태를 모르는 게 제일 나쁘다.
