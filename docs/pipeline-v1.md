# V1 — 완전 자동 파이프라인 설계

> 2026-08-08 확정. 유저의 수동 조작은 **뱅샐 내보내기 탭 3번**뿐이고,
> 그 이후는 노트북·폰 전원과 무관하게 Google 서버에서 자동으로 돈다.

## 1. 왜 이게 가능한가 — 확인된 사실

| 확인 | 결과 | 근거 |
|---|---|---|
| 뱅샐 zip 암호화 방식 | **ZipCrypto** (AES 아님) | 내보내기 2건 실측 (2026-07-26, 2026-08-08). `compress_type=8`(deflate), `flag_bits & 0x1` |
| 비밀번호 생략 가능? | **불가** — 항상 입력 필수 | 사용자 확인 |
| `Utilities.unzip()` | 암호 zip **불가** | Apps Script 오래된 제약 |
| `UnzipGs` → `zlib.js` | **ZipCrypto 지원, AES 미지원** | zlib.js 소스 확인 — `createDecryptionKey`, `updateKeys`, CRC32 기반 3키 방식 |
| 파일 크기 | 117KB (한도 50MB) | 여유 |
| 처리 시간 | 1MB 암호 zip에 60~90초 | 117KB면 훨씬 짧다. Apps Script 6분 한도 내 |

→ **암호화 방식이 맞아떨어진다.** 실제 Apps Script 실행 검증만 남았다.

## 2. UX — 유저가 겪는 것

```
[초기 설정 — 1회, 5분]
  Apps Script 스크립트 복사 → 붙여넣기 → Google 계정 승인 → 비번 1회 입력
  Claude/ChatGPT에 Google Drive 커넥터 연결

────────────────────────────────────────────────────────

[주기적으로 — 유저가 정하는 주기]
  유저:  폰에서 뱅샐 앱 → 내보내기 탭 3번        ← 유일한 수동 조작
            ↓ (메일 도착)
  자동:  Google 서버에서 시간 트리거 발동
         Gmail 검색 → zip → 복호화 → 파싱 → 정규화 → 감사 → 집계
         → Drive 저장
            ↓
  유저:  푸시 알림 "8월 리포트 준비됨"

[언제든, 어디서든, 아무 LLM으로나]
  "1억까지 얼마나 남았어?"     → Drive 읽고 답변
  "이번 달 왜 초과했어?"       → 계산된 집계에서 답변
  "구독 다 끊으면 얼마 빨라져?" → 시뮬레이션
```

**노트북도 폰도 켜져 있을 필요가 없다.**

## 3. 왜 MCP가 아닌가

`claude.ai` 웹과 ChatGPT 웹·모바일 앱은 **로컬 MCP(stdio)에 접근할 수 없다.**
유저 기기에서 프로세스를 띄울 수 없기 때문이다. 웹에서 MCP를 쓰려면 인터넷에
노출된 **원격 MCP 서버**가 필요하고, 그건 호스팅 비용이거나 배포 마찰이다.

| 클라이언트 | 로컬 MCP | 원격 MCP | **Drive 커넥터** |
|---|---|---|---|
| Claude Desktop / Code | ✅ | ✅ | ✅ |
| Cursor / Codex | ✅ | ✅ | — |
| claude.ai 웹·모바일 | ❌ | ✅ | ✅ |
| ChatGPT 웹·모바일 | ❌ | ✅ | ✅ |
| Gemini | ❌ | ✅ | ✅ |

**인제스트가 진짜 자동이면 대화로 트리거할 이유가 없다.** 알아서 되니까.
남는 건 조회·대화뿐이고, 그건 **Drive 커넥터로 전부 커버된다.**

→ MCP 서버는 **선택**으로 내린다. 데스크톱에서 더 정교한 시뮬레이션이 필요해질 때.

## 4. 핵심 설계 — Drive에는 "계산된 결과"를 놓는다

LLM에게 원본 거래 2,456건을 던지면 **함정 세 개를 매번 새로 밟는다**
(이체 이중계상 · 부호 · 환불 — 실제로 오늘 세 번 다 틀렸다).

그래서 **Apps Script가 계산까지 끝내고, LLM은 읽고 해석만 한다.**

```
Drive/k-money/
├── report-YYYY-MM-DD.md        사람이 읽는 리포트 (푸시 알림에 붙는 것)
├── snapshot-YYYY-MM-DD.json    계좌별 잔액, 종목별 원금·평가·수익률
├── ledger-summary.json         월별 수입·지출·고정/변동 (계산 완료)
├── goal-progress.json          목표 대비 위치, 도달 예상 시점
├── audit-findings.json         감사 결과 (조용히, 이상할 때만 리포트에 노출)
└── raw/                        원본 zip 보존 (소급 재처리용)
```

이러면 **산수 신뢰성**(코드가 계산)과 **자유 대화**(LLM이 해석)를 둘 다 얻는다.

## 5. 정직한 대가

### (a) 이식 비용
Python 로직을 Apps Script(JavaScript)로 다시 써야 한다.
대상: 부호 정규화 · 이체 분리 · 환불 처리 · 고정/변동 분해 · 자산 스냅샷 파싱 ·
감사 규칙 · 목표 계산.

**헛수고는 아니다.** Python 버전을 **스펙이자 검증 기준**으로 남기면 두 구현을
대조할 수 있고, 오늘 확보한 실데이터가 그대로 테스트 픽스처가 된다.

### (b) V8 런타임 제약
`UnzipGs`는 V8을 끄라고 명시한다(구식 Rhino, ES5). 코드 작성이 불편하다.

**회피 경로 (Plan B)**: ZipCrypto 복호화를 직접 구현한다. CRC32 기반 3키 방식이라
40줄 남짓이다. 복호화한 deflate 스트림으로 **암호 없는 zip을 재조립**해
`Utilities.unzip()` 에 넘기면 inflate 구현도 라이브러리도 필요 없고,
**V8을 켠 채로 현대 JS를 쓸 수 있다.**

### (c) Drive 노출면
원본 zip과 비번은 Apps Script 속성(유저 계정 스코프)에 두고,
Drive에는 가공 결과만 올린다. 유저의 Drive 공유 실수 리스크는 남는다.

### (d) Google 계정 종속
Gmail로 받고 Drive에 넣으므로 Google 계정이 전제다.
**단, 뱅샐 zip이 이미 Gmail에 오므로 신뢰 경계는 늘어나지 않는다.**
