# 배포 파이프라인 (D8)

> 코드가 바뀌었을 때 **어떻게 알리고 어떻게 최신화할 것인가.**
> 결론: **Apps Script 라이브러리 + 버전 고정.** 원격 코드 실행도, 외부 통신도 하지 않는다.

---

## 1. 왜 GitHub에서 코드를 받아오지 않는가

가장 먼저 떠오르는 방법 — 스크립트가 우리 repo에서 최신 코드를 받아 실행하는 것 — 은 **공급망 백도어**다.

이 스크립트는 **Gmail 전체 읽기 + Drive 읽기·쓰기** 권한으로 돈다. repo가 털리거나 유지보수자가 나쁜 커밋을 하나 밀면, 모든 유저의 **메일함 전체**가 그 코드에 열린다. k-money 데이터만이 아니다.

| 방식 | 원격 코드 실행 | 추가 권한 | 유저 동의 |
|---|---|---|---|
| `eval(UrlFetchApp.fetch(github))` | ⛔ **매 실행마다** | 외부 요청 | 없음 |
| Apps Script API로 자기 수정 | ⚠️ 갱신할 때 | `script.projects` — **유저의 다른 스크립트까지 수정 가능** | 없음 |
| **라이브러리 + 버전 고정** | ✅ **없음** | 없음 | **갱신마다 명시적** |

**자동 갱신에는 안전한 길이 없다.** 자동이라는 건 "이 유지보수자를 영원히, 무조건 믿는다"는 뜻이고, 1인 사이드 프로젝트가 유저에게 요구할 수 있는 신뢰가 아니다. 대신 **갱신을 한 번의 클릭으로 줄인다** — 마찰은 최소화하되 동의는 남긴다.

지금은 한 발 더 갔다. **네트워크로 받아오는 것이 아예 없다.** 배포되는 어떤 `.gs`에도 `UrlFetchApp`이 없고 매니페스트에 `script.external_request`도 없다.

`oauthScopes` 배열을 명시해 둔 것이 여기서 **보안 장치**로 작동한다. 라이브러리는 **호출 스크립트의 스코프로 돌기 때문에**, 목록에 없는 권한은 라이브러리가 쓰려 해도 던진다. 이 배열을 지우면 Apps Script 가 라이브러리의 스코프까지 합쳐 추론하고, 유저는 늘어난 동의 화면을 그냥 넘길 것이다. **장부가 아니라 통제 장치다. 지우지 마라.**

> ⚠️ 다만 **"데이터가 못 나간다"로 과장하지 마라.** 막은 것은 *스스로 보내는 HTTP 요청*뿐이다. `drive` 권한으로 파일 공유 설정을 바꿀 수 있고, `spreadsheets` 권한으로 시트에 `=IMPORTDATA(...)`를 써 넣으면 **구글 서버가 대신 요청을 보낸다.** 유저에게 하는 말은 "스스로 인터넷 요청을 보낼 수 없다"까지여야 한다. 그 이상은 거짓이고, 거짓인 게 한 번 들키면 나머지 정직한 문장까지 같이 죽는다.

## 2. 프로젝트가 둘로 나뉜다

```
┌─ 라이브러리 프로젝트 (개발자 계정, '링크가 있는 사람은 보기' 공유) ─┐
│                                                                  │
│   core.gs          집계 코어 (npm run build 산물)                 │
│   zipcrypto.gs     ZipCrypto 복호화                               │
│   app.gs           ★ 파이프라인 본체 — Gmail·Drive·메뉴·상태      │
│   library-api.gs   ★ 공개 API — 이것만이 계약이다                 │
│                                                                  │
│   → 배포하면 버전 번호가 붙는다 (1, 2, …)                         │
│   → 유저가 드롭다운으로 갈아끼운다. 여기 있는 건 고칠 수 있다     │
└──────────────────────────────────────────────────────────────────┘
                              ▲
                              │ appsscript.json 의
                              │ dependencies.libraries[]
                              │
┌─ 템플릿 Sheet + 바인딩 스크립트 (유저가 사본을 만든다) ────────────┐
│                                                                  │
│   container.gs     위임만. onOpen · runDaily · menu_* · env_()    │
│                    한 번 복사되면 우리가 못 고친다                 │
└──────────────────────────────────────────────────────────────────┘
```

### 왜 컨테이너를 얇게 유지하는가

`container.gs` 는 사본을 뜨는 순간 유저 시트 안으로 복사되고, **그 뒤로 우리가 고쳐도 닿지 않는다.** 거기 로직을 두면 버그 하나 고치는 데 유저에게 "편집기 열고 전체 선택해서 붙여넣으세요" 또는 "사본을 새로 만들고 다시 설정하세요"를 시켜야 한다. 후자는 **비밀번호(스크립트 속성)와 트리거가 따라오지 않는다.** 둘 다 사회 초년생에게 시킬 일이 아니다.

그래서 컨테이너에는 세 종류만 남긴다.

| 남는 것 | 왜 |
|---|---|
| `onOpen` · `runDaily` · `menu_*` | Apps Script 가 **이름으로** 찾는다. 단순 트리거·트리거 핸들러·메뉴 대상은 컨테이너 함수여야 한다 |
| `env_()` | **컨테이너 컨텍스트에서만 옳은 것**을 모아 넘긴다 (아래) |
| 라이브러리를 못 찾았을 때의 안내 | 그것만은 라이브러리 없이 말할 수 있어야 한다 |

`test/container.test.js` 가 이 경계를 강제한다 — `GmailApp.search`·`openById`·`KM.aggregate` 가 컨테이너에 들어오면 테스트가 깨진다. 실질 코드 줄 수 상한도 걸어 뒀다.

### ⚠️ `env` — 라이브러리에서 전역 서비스를 직접 부르지 마라

라이브러리 코드에서 아래를 그냥 부르면 **누구 것인지 모른다.**

| 부르면 | 얻는 것 |
|---|---|
| `PropertiesService.getScriptProperties()` | **라이브러리 프로젝트**의 속성. 유저 비밀번호가 거기 없다 |
| `Session.getScriptTimeZone()` | **라이브러리**의 시간대. 유저 화면의 시각이 틀어진다 |
| `ScriptApp.newTrigger()` | 어느 프로젝트에 걸리는지 불분명하다 |
| `Drive`(고급 서비스) | 라이브러리 프로젝트에서도 켜져 있어야 한다 |

`instanceof Date` 가 경계를 못 넘어 84개월짜리 산출물이 나온 적이 있다 (§6). **한 프로젝트에 다 넣고 테스트하면 재현되지 않는 종류다.** 그러니 추측하지 않는다 — 컨테이너가 자기 컨텍스트에서 만든 것을 `env` 에 담아 넘기고, `app.gs` 는 받은 것만 쓴다. `ScriptApp` 만은 컨테이너에 남겨 콜백으로 넘긴다.

**참조는 매니페스트(`appsscript.json`)에 들어간다.** 매니페스트는 스크립트의 일부라 **"사본 만들기" 때 같이 복제된다** — 유저는 라이브러리 ID를 입력할 일이 없다.

### 왜 `library-api.gs`가 따로 있나

유저는 **버전을 고정**한다. 우리가 내부를 리팩터링해도 그 유저는 예전 버전에 머물다가 어느 날 올린다. 그때 `KM.parse.extract` 같은 **내부 경로**를 직접 부르고 있었다면, 이름 한 번 바꾼 것으로 남의 자동화가 조용히 멈춘다.

그래서 내부(`KM.*`)와 공개 표면을 가른다. `library-api.gs`의 함수 이름과 인자는 **계약**이고, 바꾸려면 버전을 올리고 예전 이름을 한동안 같이 남긴다.

`container.gs`의 `api_()`는 라이브러리와 전역 양쪽에서 코어를 찾는다. 덕분에 **개발용 코드와 배포용 코드가 갈라지지 않는다** — 갈라지면 반드시 어긋나고, 어긋난 걸 늦게 안다.

## 3. 개발자 — 새 버전 내보내기

```sh
# 1. 고치고 검증
vim core/analyze.js
npm run check                                  # 빌드 + 테스트
node scripts/run-local.js fixtures/real.json   # 실데이터로 산출물 확인

# 2. 버전 올리기
npm version patch          # package.json · VERSION · container.gs · core.gs 가 함께 올라간다
npm run check              # 올린 뒤에 한 번 더 — 버전이 세 군데에서 맞는지 본다

git push && git push --tags
```

그다음 **라이브러리 프로젝트**에서:

1. `core.gs` · `app.gs` · `library-api.gs` 붙여넣기 (`zipcrypto.gs`는 거의 안 바뀐다)
2. **배포 → 새 배포** → 설명에 버전 번호
   > 배포와 버전은 통합돼 있다. 새 배포를 만들면 버전이 자동으로 생기고, 어떤 배포든 라이브러리로 쓸 수 있다.
3. 새 배포의 **정수 버전 번호**를 아래 이력에 적어 둔다. 유저는 드롭다운에서 가장 큰 번호를 고르므로, 배포 직후가 곧 최신이다
4. **`CHANGELOG.md` 에 항목을 쓴다.** 유저에게 "바뀐 것들을 보고 올릴지 정하세요"라고 안내하므로, 여기가 비면 그 안내가 통째로 헛돈다. 반드시 **🔴/🟡/⚪ 로 올려야 하는지**를 밝힌다.

   > ⚠️ **배포 번호는 배포한 **뒤에** 적는다.** 미리 적으려고 추측했다가 두 번 연속 틀렸다 (3인 줄 알았는데 4, 5인 줄 알았는데 7). 편집 중 저장된 배포가 번호를 먹기 때문에 코드 버전에서 유추가 안 된다. 유저가 드롭다운에서 고르는 게 이 숫자고, **틀리면 오류 없이 옛 코드로 돈다.**
5. **GitHub 릴리스를 만든다** — `git tag v0.1.2 && git push --tags`, `gh release create`

> 유저가 읽는 건 커밋 메시지가 아니라 `CHANGELOG.md` 다. **"무엇을 고쳤나"가 아니라 "당신이 뭘 해야 하나"**를 쓴다. 내부 구조 개선은 ⚪ 로 묶어 한 줄이면 된다.

### 라이브러리 배포 이력

| 라이브러리 버전 | 코드 버전 | 비고 |
|---|---|---|
| 1 | 0.1.0 | 최초 |

| 4 | 0.2.0 | `app.gs` 신설 — 파이프라인을 라이브러리로. 못 믿을 숫자 게이트 |
| 7 | 0.3.0 | 산출물 이름을 한국어로. 메뉴 dispatch + 예비 슬롯 |
| 9 | 0.4.0 | `AGENT.md` · `메모리/` — 세션 사이를 잇는 그릇 |

> 배포 번호는 **연속이 아니다.** 편집 중 저장된 배포가 번호를 먹는다.
> 그래서 코드 버전(0.2.0)에서 배포 번호(4)를 유추하면 안 되고,
> 배포할 때마다 실제로 붙은 숫자를 여기 적어야 한다. 유저가 드롭다운에서
> 고르는 건 이 숫자이고, 틀리면 **오류 없이 옛 코드로 돈다.**

> ⚠️ **`container.gs`를 고쳤다면 라이브러리 배포로는 전달되지 않는다.** 그 파일은 유저 시트 안의 사본이다. 템플릿 프로젝트에 붙여넣어야 **새 사본을 만드는 사람**부터 반영되고, 기존 유저에게는 끝내 닿지 않는다.

## 4. 유저 — 설치와 갱신

### 최초 설치

```
1. 템플릿 시트 링크 → "사본 만들기"
      라이브러리 참조가 매니페스트에 있어 같이 따라온다

2. 시트 메뉴 💰 돈동생 → ① 처음 설정하기
      뱅샐 zip 비밀번호를 넣고, 같은 함수가 트리거까지 건다

3. 권한 승인 1회
      "확인되지 않은 앱" 경고가 뜬다. 회피 불가
```

Apps Script 편집기도 프로젝트 설정도 열지 않는다.

### 갱신

```
메뉴 💰 돈동생 → 버전 보기
  → 시트 스크립트: 0.1.1 / 집계 라이브러리: 0.1.1
  → 최신은 GitHub 에서 확인

확장 프로그램 → Apps Script → 라이브러리 → kmoneylib
  → 버전에서 가장 큰 번호 → 저장
```

**설정과 데이터는 그대로 유지된다.** 비밀번호는 스크립트 속성에, `돈동생-*.json`·`메모리/`는 Drive에 있고, 둘 다 라이브러리와 무관하다.

> 라이브러리 버전은 **정수**(1, 2, 3…)이고 우리가 쓰는 semver(0.1.1)와 모양이 다르다. 유저에게는 "가장 큰 번호"라고 말한다. 매핑을 외우게 하지 않는다.

#### 왜 '업데이트 확인'이 없어졌나

GitHub 에서 `VERSION` 문자열을 받아 새 버전을 알려주는 메뉴가 있었다. 지웠다. 얻는 것보다 치르는 값이 컸다.

- 동의 화면에 **'외부 서비스 연결'** 한 줄이 붙는다. Gmail 전체 읽기를 이미 받는 도구에서 그 줄은 "밖으로 보낼 수도 있다"로 읽힌다. 우리가 가진 가장 강한 주장 — *"인터넷에 나갈 권한 자체가 없습니다"* — 을 알림 하나와 맞바꾸는 셈이었다
- 알림을 받아도 갱신은 어차피 편집기에서 손으로 하는 일이다. 줄여주는 수고가 거의 없다
- 네트워크·권한·404·응답형식을 전부 다뤄야 했고, 실제로 **유저에게 "업데이트 확인에서 오류"로 처음 새어 나갔다.** 부가 기능이 본 기능보다 먼저 깨졌다

지금은 `버전 보기`가 지금 도는 두 버전을 보여주고, 최신은 저장소에서 보게 한다.

> ⚠️ **`container.gs`는 어떤 갱신 경로로도 유저에게 닿지 않는다.** 라이브러리 버전을 올려도 바뀌는 건 집계 코어뿐이고, `container.gs`는 유저 시트 안에 복사돼 있다. 그래서 `버전 보기`는 두 버전을 **따로** 보여준다 — 합치면 옛 `container.gs`로 도는 걸 아무도 모른다. `container.gs`에 꼭 필요한 수정이 생기면 문서로 안내하는 수밖에 없다. 그러니 여기 로직을 넣지 말고, 고칠 여지가 있는 것은 전부 라이브러리로 민다.

## 5. 알아둘 제약

| 제약 | 영향 |
|---|---|
| 라이브러리는 실행이 **약간 느리다** | 우리 실행은 14초. 무시 가능 |
| 라이브러리 안의 **단순 트리거**는 호출 스크립트에서 안 돈다 | 우리 트리거는 `container.gs`가 만드는 **설치형**이고 핸들러도 거기 있다. 해당 없음 |
| 라이브러리 코드는 **디버깅 중 진입 불가** | 로직은 node에서 테스트한다. 애초에 여기서 디버깅하지 않는다 |
| `HEAD(개발 모드)`는 라이브러리 **편집 권한**이 필요 | 유저는 못 쓴다. 개발자 전용 |
| 유저가 버전을 안 올리면 **영원히 옛 버전** | 그게 설계다. 강제하지 않는다 |
| `container.gs`는 **갱신 경로가 없다** | 유저 시트 안의 사본이다. 로직을 두지 말고 라이브러리로 민다 |

### 스코프

`oauthScopes`는 유저 프로젝트의 매니페스트에 **명시적으로** 적는다. 라이브러리가 스코프를 밀어 넣을 수도 있지만, 그러면 유저가 무엇에 동의하는지 우리가 통제하지 못한다. 템플릿에 필요한 최소 스코프만 적고 그 목록을 문서에 공개한다.

> ⚠️ **명시하는 순간 자동 추론이 꺼진다.** `oauthScopes`가 없으면 Apps Script 가 코드를 훑어 스코프를 만들어 주지만, 적어 놓으면 **그 목록이 전부**다. 하나 빠뜨리면 그 API 만 조용히 던진다 — 나머지는 멀쩡히 돌기 때문에 늦게 안다. `UrlFetchApp`을 쓰면서 `script.external_request`를 빠뜨린 게 이 프로젝트에서 실제로 난 사고다.

### 템플릿 프로젝트 동기화 — `container.gs`와 `appsscript.json`은 **한 짝이다**

`appsscript/` 의 파일들은 **repo 에만 있는 사본이다.** 여기서 고쳐도 템플릿 시트의 스크립트는 안 바뀌고, 유저 사본은 템플릿에서 뜬다.

> ⚠️ **둘 중 하나만 붙여넣지 마라. 실제로 이걸로 깨뜨렸다.**
>
> 매니페스트에서 `script.external_request` 를 뺐는데 `container.gs` 는 아직 `UrlFetchApp` 을 부르는 옛 버전이었다. 결과: 메뉴를 누르면 *"지정된 권한으로는 UrlFetchApp.fetch 을(를) 호출할 수 없습니다"*. 코드와 권한은 같은 커밋에서 나온 것이어야 한다.

```
템플릿 시트 → 확장 프로그램 → Apps Script

  1) ⚙️ 프로젝트 설정 → "appsscript.json 매니페스트 파일 표시" 켜기
     (편집기에 보이게 하는 설정일 뿐이다. 매니페스트는 원래 항상 있고,
      꺼져 있어도 동작하며 사본에도 따라간다. 유저는 켤 필요가 없다)

  2) main 파일 → 전체 선택 → repo 의 appsscript/container.gs 로 교체
     ⚠️ 아래에 덧붙이면 안 된다. 그렇게 하다 container.gs 를 한 번 날렸다

  3) appsscript.json → repo 내용으로 교체
     ⚠️ 라이브러리 참조도 같이 덮인다. version 이 실제 배포 번호와
        같은지 저장 전에 확인해라. 다르면 저장하는 순간 다른 버전이 된다

  4) 저장 → 사본을 새로 하나 떠서 설치를 처음부터 해본다
     동의 화면의 항목이 docs/install.md 의 스코프 표와 같은지 본다
```

**기존 사본은 안 바뀐다.** 지금 열어 둔 테스트 사본이 있으면 버리고 새로 떠라. 옛 `container.gs` 가 그 안에 복사돼 있다.

**이미 사본을 만든 유저에게는 소급되지 않는다.** 템플릿을 고쳐도 남의 시트 안 사본은 그대로다. 다만 그 사본은 **유저 본인 소유**라, 위와 똑같은 절차로 자기 `appsscript.json`을 고치고 저장하면 다음 실행 때 승인 창이 다시 뜬다. 사본을 새로 만들 필요는 없다 — 오히려 새로 만들면 **스크립트 속성(비밀번호)과 트리거가 따라오지 않아** 설정이 날아간다.

그래도 남에게 편집기를 열게 하는 건 실패다. 스코프는 처음에 확정하고 되도록 건드리지 않는다.

## 6. ⚠️ 라이브러리 경계에서만 나는 버그

**한 프로젝트에 다 넣고 테스트하면 절대 재현되지 않는 종류가 있다.** 실제로 겪었다.

`getValues()` 가 만든 `Date` 는 **유저 스크립트 컨텍스트**의 객체다. 파싱 코드를
라이브러리로 옮기면 **다른 컨텍스트**에서 도는데, `instanceof` 는 그 경계를 넘지
못한다. `v instanceof Date` 가 false 가 되어 문자열 분기로 떨어졌고,
`"Fri Apr 03 2026 …".slice(0,10)` 이 날짜가 됐다. `month()` 가 `"Fri Apr"` 를 월로
잡아 **84개월짜리 산출물**이 나왔다 (366일 → 175일, 16KB → 34KB).

**수입·지출 합계는 정확히 맞았다.** 날짜와 무관한 값이라서다. 구조를 찍어보지
않았으면 못 봤을 것이다.

교훈 두 가지:

- **경계를 넘는 값은 `instanceof` 로 판별하지 않는다.** 모양으로 본다
  (`typeof v.getFullYear === 'function'`).
- **라이브러리 분리는 배포 직전이 아니라 일찍 해야 한다.** 늦게 하면 이런 버그가
  유저 손에서 처음 터진다.

관련: `core/parse.js` 의 `isDateLike()`, `test/core.test.js` 의 `node:vm` 회귀 테스트.
