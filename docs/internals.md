## 1. 기술 스택

### 1-1. 실행 환경 — 전부 Google 서버

| 계층 | 기술 | 이유 |
|---|---|---|
| 실행 | **Google Apps Script** | 시간 트리거가 Google 서버에서 돈다 → **유저 기기 전원 무관**. 인프라 계정 불필요 |
| 메일 수집 | Apps Script **Gmail Service** | 내장. GCP OAuth 클라이언트 불필요 |
| zip 복호화 | **자체 ZipCrypto 구현** (`zipcrypto.gs`) | `Utilities.unzip()`은 암호 zip 불가. UnzipGs는 Rhino가 필요한데 2026-01-31 sunset |
| xlsx 파싱 | **Drive API로 Sheets 변환 후 `getValues()`** | 엑셀 파서 이식이 통째로 불필요해진다 |
| 저장 | Apps Script **Drive Service** | 유저 개인 저장소. 우리 서버 없음 |
| 시크릿 | **Properties Service** | 코드·리포지토리에 비번이 남지 않는다 |

### 1-2. 코어 — 한 벌로 양쪽에서 돈다

**포팅 단계가 없다.** node로 검증한 **같은 파일**이 Apps Script에서 실행된다.
두 구현을 따로 두면 반드시 어긋나고, 어긋난 걸 알아채는 데 오래 걸린다.

```
core/model.js      부호 규약 · 소유자 판정 · 스냅샷 파생값
core/layout.js     뱅샐 레이아웃 ← 앱 형식이 바뀌면 여기만 고친다
core/analyze.js    집계
core/parse.js      시트 행 → 도메인 객체
core/aggregate.js  Drive에 올릴 facts JSON
       │
       │  node scripts/build-gs.js   (의존 순서대로 한 파일로 묶는다)
       ▼
appsscript/core.gs
```

> **왜 묶는가**: Apps Script는 파일 간 전역 실행 순서를 보장하지 않는다.
> 모듈이 로드 시점에 `KM.model`을 참조하므로 순서가 어긋나면 조용히
> `undefined`가 되고, 죽지 않은 채 이상한 값을 낸다.

| 도구 | 용도 |
|---|---|
| node ≥ 20 | 코어 실행·테스트. 의존성 0 |
| `node --test` | 회귀 테스트 40개 |
| Python + `uv` | **개발 도구만.** Gmail 탐색, 테스트 픽스처 생성 |

## 2. 파이프라인

**전 구간 1회 실행 = 14초.** 아래는 실측 검증된 흐름이다.

```
┌──────────────────────────────────────────────────────────────┐
│  ① 수집     Gmail 검색 → 첨부 zip → Drive/raw/ 에 원본 보존    │
│             처리한 message id 를 기록해 같은 메일을 다시 안 본다│
├──────────────────────────────────────────────────────────────┤
│  ② 복호화   ZipCrypto 자체 구현으로 해제 (550ms)               │
│             복호화한 스트림으로 무암호 zip 을 재조립해          │
│             Utilities.unzip() 에 넘긴다 (inflate 가 네이티브)   │
│             재조립 시 UTF-8 플래그를 세워 한글 파일명도 복원     │
├──────────────────────────────────────────────────────────────┤
│  ③ 변환     Drive API 로 xlsx → Google Sheets                 │
│             엑셀 파서 이식이 통째로 사라지는 지점               │
├──────────────────────────────────────────────────────────────┤
│  ④ 파싱     getValues() → 거래·잔고 객체                       │
│             헤더가 다르면 **즉시 실패** ← 조용히 틀리지 않게     │
│             합계 셀은 읽지 않는다 (수식이라 값이 없다)          │
├──────────────────────────────────────────────────────────────┤
│  ⑤ 정규화   · '이체' 분리 (수입/지출 합산에서 제외)             │
│             · 부호 규약 (지출 음수 → outflow 로 반전)          │
│             · 환불 = 지출 타입 + 양수 → 차감                   │
│             · 원화 아닌 거래는 합계에서 제외                    │
├──────────────────────────────────────────────────────────────┤
│  ⑥ 집계     월별 수지 · 카테고리 · 고정지출 · 급증 · 유휴현금   │
│             투자 손익 · **이체를 본인/타인으로 분해**           │
├──────────────────────────────────────────────────────────────┤
│  ⑦ 품질     dataQuality.flags — 판단이 아니라 **신호**         │
│             못 믿을 값은 키 자체를 만들지 않는다 (저축률)       │
├──────────────────────────────────────────────────────────────┤
│  ⑧ 델타     이전 스냅샷과 비교                                 │
│             대화 한 세션이 알 수 없는 유일한 것                 │
├──────────────────────────────────────────────────────────────┤
│  ⑨ 산출     facts-YYYY-MM-DD.json + latest.json               │
└──────────────────────────────────────────────────────────────┘
                              ↓
              Claude / ChatGPT / Gemini 가 Drive 를 읽고 대화
```

### 산출물 레이아웃

```
Drive/k-money/
├── latest.json              LLM이 읽는 것. 고정 이름이라 커넥터가 찾기 쉽다
├── profile.json             유저 컨텍스트 — **LLM이 대화로 쌓는다**
├── facts-YYYY-MM-DD.json    히스토리 (최근 12개). 델타 계산의 재료
├── status.json              마지막 실행 결과. 실패도 여기 남는다
└── raw/YYYY-MM-DD.zip       원본 보존 — 집계를 고쳤을 때 소급 재계산용
```

### 설계 원칙: 우리가 파는 건 산수가 아니라 "어떤 식을 쓸지"다

한때 감사 규칙 엔진(R1~R8 + 한국어 문장)이 있었고, 그다음엔 목표 계산 표가
있었다. **둘 다 지웠다.** 적대적 검토 결과 유저 질문 25개 중 목표 표가 필요한
질문이 **하나도 없었다.**

| 넣는다 | 뺀다 |
|---|---|
| 원본을 훑어야 나오는 것 (그룹핑·중앙값) | 식이 하나뿐인 것 (뺄셈·나눗셈 한 번) |
| 그럴듯한 식이 여럿인데 **하나만 맞는** 것 | **우리가 상수를 고른** 것 |
| 대화 한 세션이 원리적으로 모르는 것 | 문장·어투·심각도 판정 |

**"LLM이 나눗셈을 틀린다"는 틀린 논거였다.** 프런티어 모델은 순수 산수를
거의 안 틀린다. 틀리는 건 **식의 선택**이다 — `pace`를 빼면 남은 필드로 만들
수 있는 그럴듯한 공식이 여섯 개인데 **그중 넷이 부호를 뒤집는다.**

그리고 **절단은 반드시 밝힌다.** 목록을 자르며 말을 안 하면 합계를 검산한
LLM이 안 맞는 걸 보고 없는 사실을 지어낸다.

**못 믿을 값은 넣지 않는다.** `null`이 아니라 키 자체를 없앤다 — 없는 숫자는
인용될 수 없다. 우리는 유저의 프롬프트를 소유하지 않으므로 **파일 자체가
유일한 방어 수단**이다.

## 3. 데이터 스키마 (실측)

### 시트 `가계부 내역` — 정형, 헤더 1행

| 컬럼 | 타입 | 비고 |
|---|---|---|
| 날짜 | datetime | |
| 시간 | time | |
| 타입 | str | **수입 / 지출 / 이체** 3종 |
| 대분류 / 소분류 | str | 24종 / 64종 |
| 내용 | str | 가맹점명 |
| **금액** | int | **지출은 음수. 지출 타입 + 양수 = 환불** |
| 화폐 | str | KRW |
| 결제수단 | str | 17종 |
| 메모 | str | **항상 비어 있음** |

### 시트 `뱅샐현황` — 비정형, 6섹션 수직 배치

| 섹션 | 내용 |
|---|---|
| 1. 고객정보 | 이름, 성별 |
| 2. 현금흐름현황 | 항목/총계/월평균 + 월별 13컬럼 |
| 3. **재무현황** | 자산 (자유입출금·저축성·전자금융·투자성) · 부채 |
| 4. 보험현황 | |
| 5. **투자현황** | 종목별 투자원금 · 평가금액 · 수익률 |
| 6. 대출현황 | |

> **토스증권 Open API가 불필요한 이유**: 5번 섹션에 종목별 손익이 이미 다 있다.
> 이 서비스는 주문을 내지 않고 readonly 조회만 필요하다.
> 없는 것: 예수금 상세, 매수/매도 거래 내역.

## 4. 설계 원칙

| 원칙 | 내용 |
|---|---|
| **계산은 코드, 해석은 LLM** | 함정은 코드로 못 박는다. LLM은 확정된 숫자만 읽는다 |
| **조용히 검증** | 감사는 위생 요건. 이상할 때만 말한다 |
| **팔 게 없다** | 무료 OSS. 상품 추천도 광고도 없다 — **권유 자체가 없다** |
| **데이터는 유저 것** | 우리 서버 없음. 유저의 Gmail·Drive에만 있고, 파일로 소유한다 |
| **조용히 틀리지 않는다** | 스키마가 바뀌면 즉시 실패. 틀린 리포트보다 낫다 |
| **자문 안 함** | 사실·계산·비교까지. 처방은 안 한다 (`docs/product.md` §5) |

### 왜 무료여야 하는가

기존 서비스는 **어딘가에서 반드시 수익화 지점을 보여야 한다** — 뱅샐은 대출·카드·보험
중개 수수료, 카카오페이는 투자권유까지 확대 예고, 무료 앱은 광고, 로보어드바이저는
수익금의 연 9.5%.

**우리는 파이프라인을 만들어 배포할 뿐이라 그 지점이 없다.**
그리고 개인화된 금융 조언에 대가를 받는 순간 **투자자문업 인가 영역**으로 넘어간다.
무료는 선택이 아니라 구조다.
